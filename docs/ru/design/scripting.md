# Заметка о дизайне: скрипты времени установки

Статус: **раннер решён — duckscript. Python исследован и доказанно
встраиваем; принятие ожидает.** duckscript — единственный скриптовый
раннер; вариант с JavaScript отброшен (инструментарий cargo-make вокруг
duckscript полон, а где нет — вызов Python служит запасным выходом). Эта
заметка фиксирует решение и исследование встраивания Python.

## duckscript (раннер)

[`duckscriptsdk`](https://crates.io/crates/duckscriptsdk) (Apache-2.0,
скриптовый язык cargo-make) встраивается как обычная зависимость:
загрузите набор команд в `Context`, зарегистрируйте встроенные команды
shun как пользовательские, запускайте скрипты с управлением потоком и std
fs/env/net. Доказательство осуществимости живёт в
`tests/scripting_duckscript.rs`. Сам justfile не встраивается (крейт
`just` — это CLI без стабильного библиотечного API) — duckscript —
встраиваемый член этого семейства.

```toml
[package.metadata.shun.script]
runner = "duckscript"

[[package.metadata.shun.script.hooks]]
phase = "prepare"                 # prepare | post-install | pre-uninstall
script = "installer/prepare.dk"   # пакуется сборкой `shun build`
```

Встроенная поверхность shun регистрируется как команды duckscript:
`shun_progress`, `shun_emit`, `shun_fetch` (проверенные скачивания) плюс
собственные std-команды SDK (fs, env, http, process, semver, ...).

Когда сработают сценарные хуки, поток доставки будет
экспортировать язык мастера в каждый сценарный шаг как
`SHUN_LANGUAGE` (локаль, выбранная на первом шаге мастера; она же
записана в манифест установки на диске). Если язык не выбран,
переменная отсутствует. Экспорт самого факта — всё, что делает shun;
запись языка в настройки установленного приложения — задача
сценария payload.

Подводные камни, которые надо нормализовать в обёртках shun: Windows-пути
с обратными слэшами — экранирующие символы в аргументах duckscript
(передавайте пути с прямыми слэшами), а присваивание — синтаксис захвата
вывода (`x = cmd args`).

## Встроенный Python — измерено (пробный запуск 2026-09)

Всё нижеописанное выполнено по-настоящему, дважды: на хостовом
CPython 3.13.5 и на **переносимом встраиваемом рантайме**
(`python-3.13.5-embed-amd64.zip` в распакованном виде, с примером PyO3
`pyembed_runner`, положенным рядом, так что `python313.dll`/stdlib
грузятся из переносимой папки — `sys.prefix` подтвердил переносимый
каталог):

| Возможность | Результат |
| --- | --- |
| Реальный HTTPS (urllib + TLS) | работает (прямой pypi.org был локально заблокирован сетью; example.com/зеркало tencent — нормально) |
| Потоковые SHA-256 + HMAC | работает |
| AES-CTR туда-обратно, подпись/проверка RSA-2048 | работает — через wheel `cryptography`, предустановленный в переносимый рантайм (`pip --target runtime/Lib/site-packages` + включение `import site` в `python313._pth`) |
| Идентичность машины | MachineGuid (winreg), MAC (`uuid.getnode`), серийный номер тома C: (ctypes `GetVolumeInformationW`) — всё работает |
| TPM | `tbs.dll` достигнут корректно через ctypes; у прошивки пробной машины TPM отключён, поэтому `Tbsi_Context_Create` возвращает `TBS_E_TPM_NOT_FOUND` (0x8028400F — заметьте: НЕ 0x80284002, это `TBS_E_BAD_PARAMETER` от NULL-структуры параметров). Путь вызова валидирован; на железе с включённым TPM тот же код прочитает `TPM_PT_MANUFACTURER` |

Измеренные размеры: встраиваемый zip **10,9 МБ** / распакованный
**20,4 МБ** / + wheel cryptography **32,4 МБ**. Бинарник PyO3-раннера сам
по себе ~0,2 МБ. Сторонние wheel с нативными `.pyd` (как cryptography)
работают без изменений — поставляйте их внутри переносимого рантайма.

Подводные камни, зафиксированные для реальной интеграции: встроенный
интерпретатор не финализируется при drop — явно сбрасывайте stdio после
выполнения скриптов (см. пример раннера); `eval` принимает только
выражения; pip против переносимого рантайма требует `--target` плюс
правку `._pth` (либо рантайм python-build-standalone, в котором pip уже
есть).

## Встраивание WebView2 фиксированной версии — измерено

Вопрос: может ли установщик нести сам движок WebView2, питающий и
собственный UI, и разворачиваемое приложение? **Механически да —
доказано от начала до конца**; ценой остаётся payload.

- cab фиксированной версии v151.0.4129.101 x64: **307 241 094 байт
  ≈ 293 МБ** в сжатом виде, **661,1 МБ** в распакованном.
- Демо-оболочка работала против распакованного переносимого рантайма
  (`WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, уже первый зонд в
  `webview2_available`): UI отрисовался (проверено офлайн-скриншотом), и
  **все шесть процессов рендерера пришли из переносимой папки**, а не из
  системной установки Evergreen.
- Вердикт: осуществимо; цена ~300 МБ **принята** (в соответствии с другими
  паковщиками). Опасение двойной копии устранено инженерно: артефакт
  встраивает ОДНУ копию — оболочка бутстрапится из поддерева рантайма
  payload (стейджинг `extract_prefix` + учитывающее хэши переиспользование
  при распаковке), поэтому установщик и установленное приложение делят её;
  см. раздел о стратегиях WebView2 в configuration.md. Фолбэк на egui
  остаётся нижней границей с нулевой ценой для машин, где нет вообще
  ничего.


## Встроенный Python (исследовано, осуществимо)

**Вердикт: да — Rust может чисто встроить небольшой CPython.**
Доказательство — `tests/scripting_python.rs` за opt-in-фичей
`python-probe`: [PyO3](https://pyo3.rs) с `auto-initialize` встраивает
интерпретатор в процесс, исполняет настоящий Python со stdlib, вызывает
пользовательские функции Rust и отображает исключения Python в ошибки
Rust. Фича никогда не входит в сборку по умолчанию; в CI её задействует
только ветка Windows (которая резолвит `--all-features` против
предустановленного CPython).

Варианты поставки для самодостаточного установщика, зеркалящие таблицу
стратегий WebView2:

| Вариант | Несёт | Примечания |
| --- | --- | --- |
| `system` (по умолчанию) | ничего | команды `process` duckscript могут вызвать установленный python; изящно деградирует при его отсутствии |
| `embeddable` | встраиваемый пакет Windows (~12–16 МБ) | официальный `python-3.x.x-embed-amd64.zip`: `python3xx.dll` + zip stdlib + `._pth`, без прав администратора, без реестра — приватный рантайм ровно как WebView2 фиксированной версии |
| `standalone` | python-build-standalone (~30–60 МБ) | дистрибутивы под опекой [Astral](https://astral.sh/blog/python-build-standalone) (то, что поставляет `uv`); кроссплатформенные, с запиненными версиями, полнофункциональные; избыточны, если не нужны pip/нативные зависимости |

Набросок:

```toml
[package.metadata.shun.script.python]    # опциональный тяжёлый запасной выход
type = "embeddable"                      # system | embeddable | standalone
```

Отвергнутые/отложенные альтернативы:

- **RustPython** (MIT, чистый Rust) — самозаявленно не готов к продакшену,
  пробелы в stdlib, нет модулей C-расширений; привлекателен когда-нибудь,
  но не для установщиков сегодня.
- **PyOxidizer / `pyembed`** — встраивание более высокого уровня, но
  проект в режиме сопровождения; здесь достаточно одного PyO3.

Открытые вопросы перед подключением:

- Бюджет размера: допустимы ли +12–16 МБ на артефакте для продуктов,
  которые это включат? (Встраивание — opt-in по манифесту, поэтому
  артефакт по умолчанию остаётся маленьким.)
- Связка версий: PyO3 линкуется с CPython хоста сборки; поставляемый
  рантайм должен совпадать. Запиньте, собираясь против того самого
  дистрибутива, который поставляем (`PYO3_PYTHON` → распакованный каталог
  embeddable/standalone).
- Изоляция: встроенный интерпретатор в процессе (UX однофайлового
  установщика) против подпроцесса (проще изоляция сбоев) — или оба, по
  выбору на каждый хук.
- Какие хуки вообще могут эскалировать до Python (только prepare, или и
  пути post-install-ремонта?).
