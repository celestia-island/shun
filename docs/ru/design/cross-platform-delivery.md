# Заметка о дизайне: кроссплатформенная доставка

Статус: **поверхность Windows проверена и её пробелы закрыты (2026-09);
рантайм-бэкенды регистрации для Linux и macOS реализованы; мобильные
платформы (Android/iOS) и HarmonyOS исследованы — пока вне охвата.**
Эта заметка фиксирует: (a) что доказала о поставленном Windows-бэкенде
концентрированная проверка поверхности регистрации автопаковки, (b) прежде
отсутствовавшие поверхности — ярлык на рабочем столе / идентичность на
панели задач / контекстное меню, — теперь реализованные, вместе с
найденными на реальной машине особенностями политик безопасности, которые
их сформировали, (c) бэкенды Linux и macOS и (d) вывод о реализуемости
для Android, iOS и HarmonyOS (отложено).

Исполняемый инвентарь пункта (a) живёт в `tests/registration_shortcuts.rs`
и `tests/msix_pack.rs`.

## 1. Что доказала концентрированная проверка Windows (2026-09, реальная машина)

Проверено запуском настоящего `InstallFlow` на машине с Windows 11 и
обратным чтением результатов средствами самого Windows (COM-резолвер
WScript.Shell, реестр, MakeAppx из Windows SDK) — а не просмотром
собственного вывода:

| Поверхность | Результат |
| --- | --- |
| `.lnk` в меню «Пуск» резолвится через shell | **пройдено** — `TargetPath` и `WorkingDirectory` возвращаются ровно в том виде, в каком их объявил контекст установки; собранный вручную синтетический PIDL `mslnk` резолвится корректно |
| Не-ASCII пути установки (中文目录) | **пройдено** — каталог установки `顺测试目录` проходит через COM-резолвер с побайтово точным результатом |
| Бинарник `.lnk` против MS-SHLLINK | **пройдено** — заголовок, CLSID `{00021401-…}`, набор флагов (target ID list + relative path + working dir + unicode), без горячей клавиши |
| ARP-запись (HKCU) | **пройдено** — полный набор полей, эквивалентный NSIS: DisplayName/Version/Publisher/InstallLocation/DisplayIcon плюс `UninstallString`/`ModifyPath`/`RepairString` (все в кавычках, каждый открывает UI деинсталлятора через `/uninstall`) и `EstimatedSize` как DWORD; EstimatedSize совпадает с итогом манифеста payload |
| Очистка при удалении | **пройдено** — ARP-ключ, ярлык, payload, деинсталлятор, каталог — всё удаляется (покрыто `tests/install_local.rs`, здесь переподтверждено) |
| Генерация манифеста MSIX | **пройдено** — идентичность, четырёхчастная версия с дополнением нулями, XML-экранированные строки, точка входа с прямым слэшем, runFullTrust |
| Реальная упаковка MSIX (MakeAppx 10.0.26100) | **пройдено** — корректный OPC zip с `[Content_Types].xml` + `AppxManifest.xml`; произведённый `dist/shundemo-0.1.0-x64.msix` **не содержит блока подписи** (так задумано: при дистрибуции через Store его подписывает магазин, либо самоподписанный сертификат должен быть доверенным) |

## 2. Закрытие пробелов Windows (реализовано в 2026-09)

Всё перечисленное ниже вошло в код после цикла проверки; каждая поверхность
отработана тестовым набором регистрации на реальной машине.

### Ярлык на рабочем столе — `install.desktop-shortcut`

Вычисляется из политики (`always` | `never` | `ask`, конвенция NSIS-флажка —
мастер egui показывает для `ask` включённый по умолчанию переключатель,
headless-запуски отвечают «включено») и пишется рядом с ярлыком меню
«Пуск». Рабочий стол вычисляется через
**`SHGetKnownFolderPath(FOLDERID_Desktop)`** — никогда
`%USERPROFILE%\Desktop`, что неверно при перенаправленном рабочем столе
(OneDrive, доменные политики). Удаление убирает ярлык безусловно
(конфигурация могла измениться между установкой и удалением).

**Измерено на реальной машине**: политики безопасности (AV/EDR-защита от
фальшивых ярлыков и вымогателей) часто запрещают создание `.lnk` именно
на рабочем столе — на проверочной машине даже `echo x > Desktop\probe.lnk`
из оболочки с повышенными правами отклоняется, тогда как `.tmp`-файлы
пишутся свободно. Поэтому ярлык на рабочем столе — **best-effort**: отказ
записи понижается до предупреждения и никогда не валит установку
(критическая поверхность — ярлык в меню «Пуск» и ARP-запись). Тестовый
набор зондирует политику машины и проверяет как happy path, так и путь
изящной деградации.

### Идентичность на панели задач — `install.aumid`

Программное закрепление на панели задач остаётся **заблокированным
дизайном платформы** (поддерживаемого API нет; pin-хаки убрали в
Windows 10). Поставлена половина про идентичность: каждый ярлык
помечается **`System.AppUserModel.ID`** через COM-хранилище свойств shell
(`IShellLink` → `IPersistFile` → `IPropertyStore`, в
`src/targets/aumid.rs` — `mslnk` пишет только байты), поэтому группировка
на панели задач, списки переходов и *инициированное пользователем*
закрепление работают корректно. AUMID по умолчанию генерируется как
`{publisher}.{product}`; `install.aumid` переопределяет его, и приложение
должно передавать то же значение в `SetCurrentProcessExplicitAppUserModelID`.
Установки MSIX получают идентичность бесплатно через пакет. Простановка
метки — best-effort по той же причине политики (проверочная машина
отклоняет `IPropertyStore::SetValue` на файлах `.lnk` — 0x80030005 —
поэтому там метка понижается до предупреждения).

### Команды контекстного меню — `[[install.verbs]]`

Поставлен уровень 1: команды Проводника на пользователя под
`HKCU\Software\Classes\Applications\<exe>\shell\<verb>\command` —
документированная поверхность Application Registration, без повышения
прав; проявляются на exe приложения и на ведущих к нему ярлыках. Три цели
команд отображаются в командные строки на каждой платформе, которая их
реализует: `data-folder` (открывает каталог установки), `uninstall`
(запускает скопированный деинсталлятор), `app` (точка входа + аргументы).
Удаление убирает созданные им ключи команд, а контейнеры
`shell`/`Applications` — только если те пусты (команда, зарегистрированная
кем-то другим, остаётся). Уровень 2 (ассоциации типов файлов) и уровень 3
(MSIX `FileExplorerExtension`) остаются работой на будущее.

### Глубокие ссылки — `install.deep-links`

Модель доставки обещала их с первого черновика; теперь они реальны, на
каждом бэкенде, на пользователя: Windows регистрирует каждую схему как
класс протокола под `HKCU\Software\Classes\<scheme>` (пустой маркер
`URL Protocol` + команда открытия, получающая URL как `%1`); Linux
объявляет `MimeType=x-scheme-handler/<scheme>;` на лаунчере и захватывает
умолчание через `xdg-mime`; синтезируемый `Info.plist` macOS несёт
`CFBundleURLTypes`. Схемы нормализуются к нижнему регистру `[a-z0-9+.-]`
(`"MyApp://"` → `myapp`). Удаление стирает Windows-класс протокола;
удаление Linux-лаунчера оставляет обработчик бесхозным (строка в
`mimeapps.list` становится недействующей — отмечено, принято).

### Почему установщик не запрашивает повышения прав UAC

Вопрос возник после находок про ярлык на рабочем столе, и ответ держится
на трёх опорах:

1. **Всё, что пишет shun, — поверхность уровня пользователя** — HKCU,
   меню «Пуск» и рабочий стол пользователя, `%LOCALAPPDATA%`. Ничто из
   этого не требует повышенного токена, так что запрос UAC ничего бы не
   дал, добавив худший сорт шума запросов (приучение пользователей
   щёлкать не глядя). Это тот же компромисс, что делает NSIS-шаблон
   wowsp, и тот же, что стоит за *пользовательскими* установками
   VS Code / Chrome.
2. **Повышение прав всё равно не исправило бы блокировку `.lnk`**: блок —
   это файловый фильтр продукта безопасности, ключающийся на папке
   рабочего стола и расширении `.lnk` — фильтры перехватывают процессы по
   политике, а не по ACL, и повышенные процессы тоже фильтруются. (Случай
   контролируемых Windows папок ведёт себя так же: он блокирует и
   администраторов, пока приложение не внесено в белый список.)
   Правильный ответ — поставленный: деградировать до предупреждения,
   сохранив ярлык в меню «Пуск» и ARP нетронутыми.
3. **Повышенная запись в *пользовательские* поверхности — ловушка
   корректности**: процесс с повышенными правами резолвит профили иначе
   (рабочий стол административной учётной записи, `%APPDATA%` и куст
   реестра могут отличаться от учётной записи устанавливающего
   пользователя) — классический NSIS-баг ярлыков «для всех пользователей».
   Когда повышение действительно нужно, конкретный шаг повышает *сам
   себя*: бутстраппер WebView2 Evergreen несёт собственный манифест
   `requireAdministrator`, так что оболочка остаётся `asInvoker` и
   делегирует.

Общемашинная область (`Program Files`, ARP в HKLM, ярлыки для всех
пользователей) — законный *режим*, нужный некоторым продуктам — он и
поставлен ровно так: осознанный opt-in (`install.scope`), никогда не
умолчание. См. раздел 6.

### Находки о робастности — обе исправлены

- Названия продуктов с недопустимыми в именах файлов символами
  (`/\:*?"<>|`, конечные точки/пробелы) **санитизируются по стему имени**
  для каждой файловой и реестровой поверхности (имена `.lnk`, путь
  ARP-ключа) — `\` в названии продукта больше не вкладывает подразделы
  реестра.
- ARP `UninstallString` передаёт `/uninstall`, но headless-парсер оболочки
  установщика принимал только `--uninstall` — клик «Удалить» в Параметрах
  Windows запускал мастер вместо удаления. Теперь разбираются оба
  написания.

## 3. Linux и macOS (рантайм-бэкенды реализованы; артефакты упаковки — далее)

**Оба посильны, и оба делят с Windows один жёсткий предел: программного
закрепления на панели задач / в доке не существует нигде.** Рантайм-бэкенды
`Registration` поставлены; артефакты упаковки на стороне сборки (deb/rpm
через `tauri-bundler`, DMG) остаются последующей работой, потому что им
нужны собственные нативные хосты сборки.

### Linux — `LinuxRegistration` (src/targets/freedesktop.rs)

Всё, что делает Windows-бэкенд, отображается на конвенции freedesktop,
всё на пользователя (`~/.local/share/...`), без повышения прав:

- **регистрация лаунчера** = записать `<product>.desktop` (Name, Exec,
  Icon из `install.icon`, Categories и — критически —
  **`StartupWMClass`** = стем входного исполняемого файла, то самое поле,
  благодаря которому инициированное пользователем закрепление на панели
  задач / в доке группируется под правильной иконкой) в
  `~/.local/share/applications`, затем прогнать по нему
  `update-desktop-database` (безопасно пропустить, когда инструмента нет —
  DE пересканируют лениво);
- **команды контекстного меню + пункт удаления** = группы `Actions=` +
  `[Desktop Action <id>]` — всегда включая действие **Uninstall**
  («Удалить»), потому что GNOME Software / KDE Discover перечисляют только
  приложения, которые отслеживают их собственные пакетные бэкенды:
  установленное через shun приложение там никогда не появится. Три цели
  команд отображаются в `xdg-open`, деинсталлятор и точку входа +
  аргументы;
- **восстановление exec-бита** — архив payload несёт 0644 для каждого
  элемента, поэтому бэкенд chmod-ает точку входа и скопированный
  деинсталлятор обратно в 0755;
- **дерегистрация** = удалить `.desktop` + обновить базу.

Писатель `.desktop` — простая работа с данными, компилируемая (и
юнит-тестируемая) на каждой платформе; гейтируется Linux только половина,
запускающая процессы. Закрепление на панели задач / в доке **остаётся
невозможным** (кросс-десктопного API нет: избранные GNOME — внутренний
ключ gsettings, закрепления KDE живут в недокументированном appletsrc;
считайте действием пользователя). Контекстные меню файловых менеджеров
(скрипты Nautilus / сервисные меню Dolphin) остаются вне охвата.

**Форматы упаковки** (пока на стороне сборки, последующая работа):
**tarball/портативный (у shun уже есть) + deb ([cargo-deb]) + rpm
([cargo-generate-rpm])** — лучший набор — ровно то, что выдаёт
`tauri-bundler` (это библиотека, пригодная и для не-Tauri payload, как и
[cargo-packager]). AppImage = средне; Flatpak = средне-высоко; snap =
высоко, отложить. Честный предел «запускается на каждом дистрибутиве»:
glibc совместим только вперёд, и **musl-статика не может везти
WebView-приложения** (webkit2gtk тащит за собой GTK C-стек) — оболочка
доставки может быть musl-статической, но поставляемые Tauri-приложения
должны собираться против старейшего поддерживаемого бейзлайна
webkit2gtk-4.1 (эпоха Ubuntu 22.04 / Debian 12 / Fedora 37+).

### macOS — `MacOSRegistration` (src/targets/macos.rs)

- **регистрация** = найти бандл `.app`, в котором живёт входной
  исполняемый файл (ближайший предок `.app`); синтезировать минимальный
  `Info.plist` (`plist.rs`, чистый и везде юнит-тестируемый), если payload
  его не нёс; восстановить exec-бит точки входа; **снять унаследованный
  `com.apple.quarantine`** рекурсивно со всей установки (браузеры метят
  установщик, а копии на macOS сохраняют xattr — без этого поставленное
  приложение наследует гейтинг Gatekeeper, на который пользователь уже
  ответил); затем `lsregister -f` бандла — Spotlight и Launchpad
  подтянутся. Дерегистрация = `lsregister -u` (файлы убирает общий проход
  удаления). Payload из «голых» исполняемых файлов (без `.app`)
  регистрируются как no-op — конвенции портативности;
- **закрепление в доке**: **поддерживаемого API нет** (хак
  `defaults write com.apple.dock` + `killall Dock` топчет пользовательские
  настройки и ненадёжен на свежем macOS) — присутствие в
  Launchpad/Spotlight через LS-регистрацию и есть эквивалент
  обнаруживаемости;
- **подписывание остаётся обязательной процессной работой** для реальной
  дистрибуции: Developer ID + hardened runtime + `notarytool` + staple; и
  скачанная оболочка **будет транслоцирована** — обрабатывайте
  предположения о собственном пути соответственно;
- **артефакты упаковки** (последующая работа): DMG через tauri-bundler /
  `hdiutil`, `.pkg` только для административных потоков, Homebrew cask как
  канал. Поставляйте **universal2** (двойная сборка + `lipo` +
  переподпись).

[cargo-deb]: https://github.com/kornelski/cargo-deb
[cargo-generate-rpm]: https://crates.io/crates/cargo-generate-rpm
[cargo-packager]: https://github.com/crabnebula-dev/cargo-packager

## 4. Android и iOS (исследовано)

**Сначала переформулировка: на мобильных «установка» принадлежит платформе
и проверяется подписью. Потоковой распаковки zstd-tar каталога приложения
в выбранное пользователем место здесь не существует.** Честная мобильная
роль shun — **конвейер сборки/упаковки/подписи** («cargo-dist для
мобильных»), а не рантайм-установщик.

### Android

- **Механика упаковки**: APK = подписанный zip (DEX + ресурсы + `.so` на
  каждый ABI); конвейер `aapt2` → `d8`/`r8` → package → `zipalign` →
  `apksigner`. AAB — формат публикации в Play (обязателен для новых
  приложений); сайдлоадингу нужен конкретный APK (`bundletool build-apks`
  + переподпись). Rust-таргеты — Tier 2 с хостовыми инструментами.
- **Живой инструментарий (2025–2026)**: `tauri android build` из Tauri 2
  (оборачивает cargo-mobile2 + Gradle; keystore через
  `keystore.properties`), **cargo-ndk** (поддерживается), крейт **`apk`**
  (aapt2/d8/zipalign/apksigner без Gradle). **xbuild и cargo-apk мертвы
  или дремлют** — не стройте на них. Мобильная Tauri 2 официально
  стабильна; сторона Android зрелее, чем iOS.
- **Рантайм-установщик: нереализуем/бессмыслен.** Пакетный менеджер ОС
  ставит из подписанного APK с подтверждением от пользователя (тихо —
  только для device-owner/MDM); APK *и есть* установщик. Политика Play
  дополнительно **запрещает самообновление / скачивание исполняемого
  кода** — рантайм-апдейтер в стиле shun был бы нарушением политики для
  любого приложения, распространяемого через Play. Сайдлоадинг деградирует
  по дизайну: **принудительная проверка разработчика при сайдлоадинге
  стартует 2026-09-30** (непроверенные приложения попадают в многошаговый
  поток с 24-часовым ожиданием).
- **Ярлыки**: значки на главном экране и ярлыки приложения
  (`shortcuts.xml`, `ShortcutManager`, `requestPinShortcut`) — **только
  объявляются приложением** — API внедрения на этапе установки не
  существует. Аналог на этапе сборки — генерация `shortcuts.xml`/
  intent-фильтров в APK, который пакует shun.

### iOS

- **Механика упаковки**: IPA = zip с `Payload/App.app` +
  `embedded.mobileprovision` (App ID + entitlements + сертификат +
  Ad Hoc-белый список UDID). Каналы: App Store, TestFlight, Ad Hoc
  (100 устройств/тип/год), Enterprise. **Инструментарий подписи (codesign,
  xcodebuild, keychain) — только macOS** — жёсткое требование к хосту.
- **Рантайм-установщик: нереализуем** вне двух ниш: (a) Ad Hoc
  OTA-манифесты (`itms-services://?...manifest.plist`) — легко, легально,
  нишево; (b) режим веб-дистрибуции ЕС / альтернативных маркетплейсов —
  реален, но за шлюзом соответствия требованиям Apple + нотаризация +
  условия комиссий октября 2026 (5% Core Technology Commission), и только
  для ЕС. Сайдлоадинг с бесплатным Apple ID (AltStore/Sideloadly) —
  хобби-путь на 7 дней/3 приложения, не канал для продукта.
- **Ярлыки**: на этапе установки не существует ничего ни в одном канале —
  значки на главном экране, схемы URL, универсальные ссылки объявляются
  приложением и проверяются подписью.
- **egui-фолбэк**: Android = `android-activity` + winit + wgpu
  (Vulkan/GLES); iOS = winit + wgpu (Metal), встроенные в UIKit-хост через
  FFI + Xcode-проект. Ни у одного нет истории «из коробки» — конвейер
  упаковки shun и есть недостающий кусок.

## 5. HarmonyOS (исследовано)

**Вывод сразу: «shun поддерживает HarmonyOS» в 2026 может честно означать
ровно одно — цель упаковки/подписи на этапе сборки, производящую
подписанные для релиза артефакты HAP/APP, плюс поток `hdc install` для
устройств разработки. У рантайм-установщика (NSIS-половины shun) на
HarmonyOS NEXT нет ни правовой, ни технической основы.**

Ландшафт (2025–2026): HarmonyOS NEXT (5.0, октябрь 2024) выбросил слой
совместимости с APK; целевая линия — HarmonyOS 6+ (API 20/23), только
Китай, только AppGallery, ~19% ОС-рынка Китая. OpenHarmony — открытая
база; коммерческий HarmonyOS — продукт Huawei поверх неё — паковщик
целится в коммерческий.

- **Формат пакета**: HAP (zip: `module.json5`, байткод ArkTS, нативные
  `libs/<abi>/*.so`); общие пакеты HSP/HAR; `.app` = пакет подачи в
  AppGallery (`pack.info`). Инструментарий пригоден для CLI: `ohpm` +
  `hvigorw assembleHap` + `hap-sign-tool` + `app_packing_tool.jar`
  (официально поддерживаемые headless-сборки CI).
- **Подпись**: SHA256withECDSA; keystore `.p12` + `.cer` + профиль `.p7b`
  (имя бандла, разрешения, а для debug — белый список UDID устройств);
  сертификаты **выдаются Huawei через AppGallery Connect**
  (индивидуальная регистрация бесплатна — без платы в стиле Apple).
- **Rust**: `aarch64/armv7/x86_64-unknown-linux-ohos` — **Tier 2 с
  хостовыми инструментами** (готов к rustup с 1.78). Коммьюнити-тулчейн
  `ohos.rs` (`cargo-ohos`, `napi-ohos`, `ohos-openssl`) — связующий клей;
  Rust-ядро + ArkTS-оболочка — проверенная архитектура (RustDesk OHOS).
  **egui заблокирован**: у winit нет апстрим-бэкенда OHOS (только
  коммьюнити-беты). **Tauri**: официальная, но не смерженная ветка
  `feat/open-harmony` (патчи wry/tao, CLI `cargo tauri ohos`) работает
  сегодня, но движется быстро — ждите перепривязки версий каждые несколько
  месяцев.
- **Честность о дистрибуции**: потребительский сайдлоадинг фактически
  закрыт (только AppGallery; `hdc install` требует режима разработчика +
  подписи Huawei + UDID). Релиз на именованные устройства: 100
  устройств/год, 90-дневная годность. Корпоративная дистрибуция сейчас
  ограничена корпоративными ПК Qingyun. **HarmonyOS PC** реален (ARM,
  дистрибуция через магазин, сайдлоадинга пока нет) — Huawei *заявила
  намерение* открыть сайдлоадинг на ПК позже; это единственный пункт
  наблюдения, который однажды мог бы оправдать там десктопный рантайм
  доставки.

Таблица усилий: цель упаковки HAP — **средне**; кросс-шаг Rust —
**легко–средне** (обёртка clang из SDK как линкер, ohos-openssl для TLS);
упаковка Tauri-on-OHOS — **средне–трудно** (не смержено в апстрим);
egui-фолбэк — **трудно** (нет winit); рантайм-установщик/флешер —
**нереализуемо**.

## 6. Область установки и декларативный мастер (реализовано в 2026-09)

### Область установки — `install.scope = user | machine | ask`

Пользовательская область остаётся умолчанием (см. «Почему установщик не
запрашивает повышения прав UAC»). `machine` — или `ask`, отвеченный «для
всех пользователей», — переключает каждую поверхность регистрации на её
эквивалент для всей машины: ARP-запись под **HKLM**, ярлык в **общем меню
«Пуск»** (`%ProgramData%`), ярлык на рабочем столе — на **общем рабочем
столе** (`FOLDERID_PublicDesktop`), команды и глубокие ссылки под
`HKLM\Software\Classes`. Оболочка определяет выбранное разрешение **до**
запуска потока и, ещё не повышенная, перезапускает себя через команду
`runas`, неся ответы пользователя (`--silent --mode=… --dir=…
--scope=machine`): согласие UAC — единственный запрос, показанный только
для режима, которому оно нужно, — паттерн бутстраппера, ровно как
обещано. Удаление зеркально (ARP `UninstallString` запускает
деинсталлятор, который повышается так же). Машинная область — только
Windows; бэкенды Linux/macOS явно её отвергают. Интеграционный тест
пропускается, пока раннер не повышен (запуск `cargo` из оболочки
администратора его задействует).

### Конвейер мастера — `[[package.metadata.shun.steps]]`

Мастер — теперь декларативный, упорядоченный, свободно компонуемый
конвейер вместо фиксированной последовательности режим → установка. Пять
видов шагов:

```toml
[[package.metadata.shun.steps]]
kind = "mode"                    # режим доставки + каталог; встраивает
                                 # переключатели `ask` (ярлык на рабочем столе, область)
[[package.metadata.shun.steps]]
kind = "scope"                   # отдельный выбор user/machine
[[package.metadata.shun.steps]]
kind = "license"                 # панель лицензии (license / license-locales)
[[package.metadata.shun.steps]]
kind = "content"                 # произвольная markdown-панель
title = "Release notes"
markdown = "notes.md"         # относительно манифеста
[[package.metadata.shun.steps]]
kind = "install"                 # запуск доставки (ровно один обязателен)
```

Отсутствие `steps` = конвейер по умолчанию (режим →
лицензия-если-объявлена → установка) с легаси-`custom-steps`, внедрёнными
после их ключей `after`; объявить и то и другое — конфигурационная ошибка,
как и ноль или несколько шагов `install`. Вопрос области и переключатель
ярлыка на рабочем столе проявляются там, где политики `ask` встречают
панель: встроены в шаг режима или отдельны (`scope`) — разработчик
компонует. Документы content и лицензий читаются **на этапе сборки** и
встраиваются в `shun-steps.json` (`ShunConfig::resolve_steps`), поэтому
рантайм-установщики не несут файловых зависимостей. Фолбэк на egui
рендерит весь конвейер (шкала шагов, гейтинг лицензии, навигация
назад/вперёд); Tauri `ShellView` отдаёт разрешённые шаги веб-фронтенду.

**Отложено решением (2026-09)**: Android, iOS и HarmonyOS — исследования
из разделов 4–5 остаются в силе; ничего из этого не запланировано.

**Следующие в очереди**:

1. Артефакты упаковки deb/rpm через `tauri-bundler` (Linux CI), DMG через

2. Контекстное меню Windows, уровень 2 (ассоциации типов файлов), если
   потребителю это понадобится.
3. **Никогда**: рантайм-установщики / внедрение ярлыков на любой телефонной
   ОС; закрепление на панели задач / в доке где бы то ни было; snap — пока
   не оправдает свою сложность.
